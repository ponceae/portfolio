Overview

A command line Blackjack game built in Python with persistent player profiles, wagering, splitting, insurance, and modular game logic. The project separates game orchestration, rule validation, payouts, storage, and terminal interaction while using structured objects to manage round state.

Architecture

The game is organized as a Python package with gameplay logic separated into modules for game state, player actions, conditions, and payouts. Dataclasses are used to represent core entities such as player and dealer hands, while the main game loop coordinates each phase of the round.

    Game Loop

  • Controls round progression and determines when control passes between the player and dealer.

    • Game state / models

  • Stores hands, wagers, bank values, insurance, and route state.

    • Conditions & Actions

  • Validates whether actions such as hit, stand, split, or double down are allowed and applies to them.

    • Payout Logic

  • Resolves blackjack, wins, losses, pushes, insurance, and doubled wagers.

    • Testing

  • Tests the individual modules and full gameplay paths independently.

Key Features / Gameplay Logic

The game supports the full round lifecycle, including player actions, dealer logic, rule validation, and payout resolution. More complex actions such as splitting require each hand to maintain its own cards, wager, and outcome state.

    Player Actions

  • The player can choose from several actions during a hand, with each action validated against the current game state before it is executed.

    • Hit

  • Draws another card and reevaulates the hand.

    • Stand

  • Ends play for the current hand.

    • Double Down

  • Increases the wager, draws one final card, then ends the hand.

    • Split

  • Separates a qualifying starting hand into two independently played hands.

    • Insurance

  • Allows a side wager when the dealer shows an Ace.

    Rule & Game State Logic

  • Game rules are evaluated continuously as the round progresses, allowing the program to determine which actions are valid and when control should move to the next phase.

    • Hand Evaluation

  • Calculates hand totals and sdjusts Ace values between 1 and 11 to avoid unecessary busts.

    • Action Validation

  • Checks whether actions such as split or double down are currently allowed.

    • Turn Progression

  • Tracks when a player hand is complete and determines when control should move to another hand or to the dealer.

    • Dealer Logic

  • Automatically draws or stands according to the dealer rules.

    • Round Conditions

  • Detects states such as blackjack, busts, completed hands, and other conditions that can end or alter the round.

    Outcome & Payout System

  • Once play is complete, the game compares the player and dealer states to determine the result of each hand and update the player's bankroll accordingly.

    • Blackjack

  • Applies the blackjack payout when the player has a natural 21.

    • Standard Win / Loss

  • Resolves the wager based on the final hand values.

    • Push

  • Returns the original wager when the player and dealer tie.

    • Insurance

  • Resolves the insurance side bet separately from the main hand.

    • Double Down

  • Uses the increased wager when calculating the final payout.

    • Split Hands

  • Resolves each split hand independently, allowing different outcomes within the same round.

Challenges / What I Learned

Testing Interactive CLI Behavior

Testing a command line game was difficult because much of the gameplay depended on input() and printed output. I learned to use pytest tools such as monkeypatch and capsys to simulate user actions and verify terminal responses, which made it possible to automate full gameplay scenarios instead of testing them manually.

Managing Split Hand State

Adding split functionality introduced multiple player hands that each needed their own cards, wager, turn state, and outcome. I refined the implementation so each split hand used the same PlayerHand structure as a normal hand, allowing the rest of game logic to handle them consistently without relying on special cases.

Refining the Object Model

As the project grew, I had to reconsider where different pieces of state and behavior belonged. Separating generic hand behavior from player and dealer specific responsibilities helped me better understand class design, inheritance, and how assigning responsibility to the correct object can keep a codebase easier to maintain.
